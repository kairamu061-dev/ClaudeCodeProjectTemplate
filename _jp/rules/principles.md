# 原則

すべての文書・チケット・コードに共通する考え方。

---

## 測ったことと推測したことを分ける

すべての主張に **測った**（根拠を添える）か **推測**（何を確かめれば決着するかを添える）の印を付ける。
バグ票、確認依頼と報告、dev-notes のすべてに当てはまる。

- 推測は書いてよい。**推測を測った結果のように書くのは不可**
- 別のプロセスや別の製品から借りてきた症状は、測った結果ではなく推測である。
  「同じ API を使っている」は「同じ症状が出る」ではない
- 推測を測った結果の口調で書くと、その文書は前例としての価値を失う

## 経緯ではなく不変条件を書く

コードのコメントには「なぜこうしたか」よりも「これを変えると何が壊れるか」を書く。
経緯は dev-notes.md とチケットに書く。コードにも重複して書くと、両者が食い違っていく。

## 原則は同じセッションのうちに全箇所へ適用する

ルールが決まったら（「この呼び出しは UI スレッドで実行してはならない」
「これは finally で解放しなければならない」など）、他に当てはまる箇所を grep して、その場で直す。
教訓を書き留めることは、それを適用することではない。教訓を書いたまさにそのセッションで
破られたことがある。

## 定義は1か所に置く

定義・構成・一覧は、ちょうど1つのファイルにだけ置く。他のファイルは書き直さずにそこへリンクする。
2つの写しは食い違っていき、どちらが正しいのか誰にも分からなくなる。
