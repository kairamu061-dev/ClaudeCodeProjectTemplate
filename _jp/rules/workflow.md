# ワークフロー

機能開発の進め方。実装の前にドキュメントを作る。

---

## プロジェクトを始めるとき

1. `docs/project_overview.md`、`docs/glossary.md`、`docs/tags.md` が無ければ作成する
2. 最初の実装の前に `docs/testing.md` を埋める（`rules/automated-tests.md` を参照）

## 新しい機能を始めるとき

1. `/add-feature <feature-area>` を実行し、ディレクトリ・テンプレート・index.md を一度に用意する
2. overview.md → spec.md → design.md の順に内容を書く
3. spec.md を書いたら、分割が必要か評価する（「分割ルール」を参照）
4. 分割が必要なら `/add-feature <sub-item-path>` を実行する
5. tasks.md に内容を書き、実装を始める

## 実装中

- 判断・問題・変更は、起きたときに dev-notes.md に記録する。
  作業ログではなく、判断の記録として書く
- 要件が変わったら、関係するドキュメントをすぐに更新する
- スキル・権限・情報が足りないときは、その要望を dev-notes.md に記録する

## 実装後

1. tasks.md のステータスを更新する
2. 実装が設計から外れた場合は、design.md を更新し、差分を dev-notes.md に記録する

## コミット

- 論理的なまとまりごとにコミットする（例：サブ項目を1つ終えるごと、ドキュメントの節を1つ書くごと）
- 関係のない複数の変更を1つのコミットにまとめない
- 区切りのよいところで GitHub に push する

---

## 分割ルール

**既定は分割する。独立して実装できる単位は、すぐにサブ項目として切り出す。**

### 分割の基準

次のいずれかに当てはまれば分割する。

- 独自の画面・ビュー・UI を持つ
- 独自のデータ定義やスキーマを持つ
- 他の単位が無くても実装・テストできる
- 別の開発者が並行して作業できる

### 例外 — 両方の条件を満たすときだけ統合してよい

- 分割すると、どちらの半分も単独では確認できない
- かつ、コードと責務がごく小さい（1クラス / 1ファイル相当）

### 手順

1. spec.md を書いた直後に分割を評価する
2. 分割対象が見つかったら、ためらわず `/add-feature <sub-item-path>` を実行する
3. 親の design.md / tasks.md には、サブ項目へのリンクと横断的な事項だけを書く
4. 分割した後も、親の overview.md と spec.md はそのまま残す（削除しない）
