# 確認ループ

自分で製品を動かせないとき（対象 OS が無い、ハードウェアが無い、CI でしかビルドできない）に読む。
その場合、すべての挙動は**実機での別の確認セッション**で確かめる。

依頼は `tmp/確認/` に置き、報告は `tmp/フィードバック/` に返ってくる。どちらも1回ごとに
`old/` へ移す（構成は `rules/structure.md`）。

---

## 1回ごとの流れ

1. 変更を push し、CI が成功するのを待つ
2. `/verify-request <title>` を実行して依頼の文書を生成する
   — 成果物を自分で測るので、数値の書き写し間違いが起きない
3. 各項目を埋め、それぞれに陰性対照を書く
4. フィードバックが届いたら：報告された点を直し、票と test-cases を更新し、
   両方の文書を `old/` に移してから、次の回を始める。確認セッションは各依頼の末尾に
   埋め込まれた「報告の書式」で返答する。その「未了・判定できなかった項目」の節は、
   次の依頼に自動で引き継がれる

## 依頼の文書のルール

この4つのルールは、どれも破ったことで1回分を無駄にしたか、不具合を出荷したことから生まれた。

- **事実はすべて、書く時点で取り直す。** サイズ、ハッシュ、パス、レジストリキーは、
  成果物と製品から取る。記憶や以前の文書から取らない。依頼の文書に書いたパスや数値は、
  それ自体が1つの主張である
- **期待値が `0` のときは、対照を一緒に示す。** `1` になるケースか、数えている文字列が
  出荷されたバイナリに存在する証拠のどちらか。そうでないと `0` は「安定している」と
  「一度も実行されていない」の両方を意味し、区別できない
- **項目を書く前に、対照が存在することを確かめる。**「旧ビルドならこれに失敗する」は
  予測である。比較を頼む前に、旧ビルドが実際に失敗することを確かめる。
  対照が存在しない項目は判定できない
- **すべての主張に 測った か 推測 の印を付ける**（`rules/principles.md` を参照）。
  依頼のテンプレートにはそのための節がある

## フィードバックの読み方

- **「判定できなかった」は結果であって、欠落ではない。** 合格よりも多くを語ることが多い。
  手がかりとして扱い、決して「問題なし」に丸めない
- 確認セッションが頼んだよりも強い方法を使ったときは、**その方法をテストケースの手順に移す**。
  次の回で弱い方法に戻らないようにするため
- 効く回避策は、原因を特定したことにはならない。両者は分けて記録する
