# エージェントルール

このファイルは、プロジェクト共通の開発プロセスとドキュメント規約を定めるものです。
実装タスクを受けたら、このルールに従って着手前にドキュメントを整えてください。

---

## ワークフロー

### 新しい機能を始めるとき
1. `docs/project_overview.md`・`docs/glossary.md`・`docs/tags.md` が無ければ作成し、
   最初の実装より前に `docs/testing.md` を埋める（「自動テスト」を参照）
2. `/add-feature <feature-area>` を実行し、ディレクトリ・テンプレート・index.md を一度に用意する
3. overview.md → spec.md → design.md の順に内容を書く
4. spec.md を書いたら、分割ルールに従って細分化が必要か評価する
5. 細分化が必要なら `/add-feature <sub-item-path>` を実行する
6. tasks.md に内容を書き、実装を始める

### 実装中
7. 判断・問題・変更は、発生した時点で dev-notes.md に記録する
8. スキル・権限・情報が不足している場合は、その依頼を dev-notes.md に記録する

### 実装後
9. tasks.md のステータスを更新する
10. 実装が設計から外れた場合は、design.md を更新し、差分を dev-notes.md に記録する

### コミット
- 論理的な作業単位ごとにコミットする（例: サブ項目の完了ごと、ドキュメントの節を書き終えるごと）
- 無関係な変更を 1 つのコミットにまとめない

## 分割ルール

**既定は分割する。独立して実装できる単位は、すぐにサブ項目として切り出す。**

### 分割の基準

次のいずれかに当てはまれば分割する:

- 独自の画面・ビュー・UI を持つ
- 独自のデータ定義やスキーマを持つ
- 他の単位が無くても実装・テストできる
- 別の開発者が並行して作業できる

### 例外 — 統合が許されるのは、次の 2 つを両方満たすときだけ

- 分割すると、どちらの半分も単独で検証できない
- かつ、コードと責務が極めて小さい（1 クラス / 1 ファイル相当）

### 手順

1. spec.md を書いた直後に分割を評価する
2. 分割対象が見つかったら、迷わず `/add-feature <sub-item-path>` を実行する
3. 親階層の design.md / tasks.md には、サブ項目へのリンクと横断的な事項だけを書く
4. 分割後も、親の overview.md と spec.md はそのまま残す（削除しない）

## バグ票のワークフロー

### バグが報告されたら
1. `issues/tickets/` にある最大の番号を確認し、次の ID を割り当てる
2. `issues/templates/BUG-template.md` を使って `issues/tickets/BUG-{NNN}.md` を作成する
3. `issues/index.md` に状態 `Open` で行を追加する
4. 原因を調査し、コードを修正する
5. 票に原因・修正内容・関連するコミットハッシュを書き、状態を `Fixed` に変える
6. 票のファイルは、修正コミットと一緒に（または直後に）コミットする

### ルール
- バグ票はすべて `issues/tickets/` に置く — 機能エリアの `tasks.md` や `dev-notes.md` には書かない
- 根本原因ごとに 1 票。原因を共有する票同士はリンクする
- 修正が確認されたとユーザーが認めるまで、票を `Closed` にしない
- **測ったことと推測したことを分ける。** どの票でも、症状・原因・影響のそれぞれに、
  どちらなのかを明記する。推測を測定の口調で書くと、票の前例としての価値が失われる
- **確認で完了できなかった段は、閉じた問題ではなく未解決のリスクである。**
  原因が自分のコードの外にあると考えられる場合でも票に記録する —
  利用者はその段を越えられなければ製品を使えない

## 確認ループ（自分で製品を動かせないとき）

エージェントが製品を実行できない場合（対象 OS が無い、ハードウェアが無い、CI でしかビルドできない）は、
すべての挙動を**実機上の別の確認セッション**で確かめる。

```
tmp/確認/          request documents written by the agent  (verification requests)
tmp/フィードバック/  reports written by the verification session
tmp/確認/old/, tmp/フィードバック/old/   archive after each round
```

### 各回の流れ
1. 変更を push し、CI が緑になるのを待つ
2. `/verify-request <title>` を実行して依頼書を生成する
   — 成果物をスクリプト自身が測るので、数字を写し間違えることがない
3. 各項目を埋め、それぞれの負の対照を書く
4. フィードバックが届いたら: 報告された点を直し、票と test-cases を更新し、
   両方の文書を `old/` に移してから次の回を始める。確認セッションは、
   各依頼書の末尾に同梱された「報告の書式」で返答する。その「未了・判定できなかった項目」の節は、
   次の依頼書へ自動で持ち越される

### 依頼書のルール

この 4 つのルールは、どれも破ったせいで 1 回分を無駄にしたか、欠陥を出荷したことから来ている。

- **すべての事実を、書く時点で取り直す。** 大きさ・ハッシュ・パス・レジストリキー —
  成果物と製品から取り、記憶や以前の文書から取らない。
  依頼書に書いたパスや数字は、それ自体が主張である
- **期待値が `0` のときは、対照を並べて示す。** `1` になる場面か、
  数えている文字列が配布バイナリに存在する証拠のどちらか。
  そうしないと `0` は「安定していた」と「一度も実行されなかった」の両方を意味し、区別できない
- **項目を書く前に、対照が存在することを確かめる。**「旧ビルドならこれに失敗する」は
  予測である。誰かに比較を頼む前に、旧ビルドが実際に失敗することを確かめる。
  対照が存在しない項目は判定できない
- **すべての主張に 測った（measured）か 推測（inferred）かを付ける。** 依頼書の雛形には
  そのための節がある。推測は構わないが、測定を装った推測は許されない

### フィードバックの読み方
- **「判定できなかった」は欠落ではなく結果である。** 合格よりも多くを語ることが多い —
  手がかりとして扱い、決して「問題なし」に丸めない
- 確認セッションが依頼したより強い方法を使ったときは、**その方法をテストケースの手順に移す**。
  そうしないと次の回で弱い方法に逆戻りする
- 効いた回避策は原因を特定したことにはならない。両者は分けて記録する

## 移植・書き換えのための退行の網

UI フレームワーク・ランタイム・その他の層を丸ごと置き換えるときは、
**旧 `spec.md` の機能一覧のすべての項目**を 済 / 要 / 差
（完了 / 要確認 / 意図的に異なる）に対応付けた網羅表を作る。

- **表の起点は、旧テストケースではなく spec の機能一覧に置く。**
  テストケースの無い機能は、テストケースから作った表には現れず、黙って落ちる。
  実際に起きたことがある: 「非同期読み込み」という仕様項目が移植で失われ、
  数週間後に利用者が遅さを報告するまで気づかれなかった
- 表は**旧実装がまだ動いているうちに**作る。旧実装を取り除いたら、
  比較は二度と取れない
- 段階的な確認は各段で追加したものしか見ないので、移植が忘れたものは捕まえられない。
  それができるのはこの表だけである

## 自動テスト

**初日に線を引く。** 実装を始める前に、どのコードが対象 OS やハードウェア無しで
テストできるかを決め、そのテストを最初のコミットから CI に載せる。

- 「全部 UI / プラットフォームのコードだから」で判断を先送りしない。純粋なロジック
  （書式の整形、引数の解釈、直列化の往復、パスの判定、比較子、木の形）は、
  たいてい数千行あり、まさに黙って壊れる場所である
- テストの段は公開・パッケージングの段の**前**に置き、失敗したら成果物が作られないようにする
- 線引きは `docs/testing.md` に記録する: 何をカバーしているか、何が対象環境を必要とし
  そのため手動の確認ループに残るか、そしてその理由

## ガイドライン

- 実装の前にドキュメントを作る
- 実装中に要件が変わったら、関連するドキュメントをすぐに更新する
- dev-notes.md は作業ログではなく、判断の記録として書く
- **経緯ではなく不変条件を書く。** コードのコメントでは「なぜこうしたか」より
  「これを変えると何が壊れるか」を優先する。経緯は dev-notes.md と票に書く。
  コードにも重ねて書くと、両者が食い違っていく
- **原則は、同じセッションのうちにすべての面へ適用する。** ルールが定まったら
  （「この呼び出しは UI スレッドで実行してはならない」「これは finally で解放しなければならない」）、
  それが当てはまる他の箇所を grep して、その場で直す。教訓を書き留めることは
  適用することではない — 教訓を書いたまさにそのセッションで破られたことがある
- 区切りのよいところで GitHub にコミット・push する
- `_jp/` 配下のファイルは読み込まない・参照しない — このディレクトリは人間の参照専用である
